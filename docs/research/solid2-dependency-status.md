# Solid 2 dependency status

Checked 2026-10-05 against live npm metadata, GitHub APIs, migration diffs and selected published sources. This refreshes the September investigations linked from [decision map #494](https://github.com/carere/zaidan/issues/494), without changing its approved dependency choices or implementing the migration.

Repository baseline: latest `main` at `5adb9fb50e50398a7bc2d9d01e8444fcdff24cc4`, merged without conflicts into draft [PR #501](https://github.com/carere/zaidan/pull/501), branch `refactor/solid-2`. The PR previously contained only a planning entry point. Its runtime, registry sources and package manifest still target Solid 1.

## What changed since the September research

- **Lucide is released:** migration PR4751 merged October 2; the published Solid 2 package is **`@lucide/solid@1.52.0`**, not an upgrade of `lucide-solid`. A temporary icon bridge is no longer required solely for lack of an upstream artifact. Import names and registry dependency strings need migration. [PR](https://github.com/lucide-icons/lucide/pull/4751), [exact artifact](https://registry.npmjs.org/@lucide/solid/1.52.0).
- **MDX has upstream migration source:** open [PR4](https://github.com/nksaraf/solid-mdx/pull/4), from `GetCommunity/solid-mdx:solid2`, replaces the legacy provider APIs. Assess it before independently porting the provider. There is still no published Solid 2 `solid-mdx` package.
- **The runtime baseline advanced:** Solid/web/compiler/Babel are now rc.13, and the renamed Vite plugin is next.47. Older research selected rc.7/next.40. [Runtime](https://registry.npmjs.org/solid-js/2.0.0-rc.13), [plugin](https://registry.npmjs.org/@solidjs/vite-plugin/3.0.0-next.47).
- **TanStack has newer published RCs and a newer unpublished compatibility fix.** Published RCs are not automatically compatible with the newest runtime; details below.
- **Cmdk already has a published v2 track.** This corrects any unsupported classification, but the approved replacement with Kobalte Search remains a separate product/architecture decision. [Artifact](https://registry.npmjs.org/cmdk-solid/2.0.0-rc.0), [approved choices](https://github.com/carere/zaidan/issues/498#issuecomment-5604066135).
- **Kobalte has newer branch fixes**, but its published core/utils still pin different old runtime RCs. Embla and Sonner migration PRs remain open.

## Classification

“Published support” means an upstream artifact targets Solid 2, including prereleases. It does **not** certify Zaidan behavior or compatibility with rc.13. `latest`, `next`, `alpha`, `beta`, and `rc` tags are mutable and do not consistently identify the newest compatible artifact. Select exact versions during implementation.

## Implications for Zaidan's existing decisions

The decisions already explicitly mandate replacing Corvu with Kobalte2, cmdk with Kobalte Search, Sonner lifecycle with Kobalte Toast, and dnd-kit with primitives drag-drop. Those choices were not merely absence-of-upstream-support fallbacks. [Issue494](https://github.com/carere/zaidan/issues/494), [approved adapter boundaries](https://github.com/carere/zaidan/issues/498#issuecomment-5604066135).

1. **Update readiness reporting:** cmdk has a released v2 prerelease. It should no longer be classified as unsupported/no migration, even though the approved Search replacement remains in force. Corvu should be classified as canonical packages unsupported with stale upstream migration branch and a separately published community fork; Sonner as open draft migration PR.
2. **Retain approved replacements:** Kobalte alpha2 already ships Calendar, Drawer, OTP, Resizable, Search and Toast per existing exact-artifact investigation [issue496 resolution](https://github.com/carere/zaidan/issues/496#issuecomment-5593748124). No change to the selected foundation follows automatically from cmdk's v2 publication. If the maintainer revisits Search, cmdk rc0 is now a concrete upstream alternative with less wrapper API migration.
3. **Check latest RC installation:** Kobalte core alpha2 pins rc3 while its utils alpha0 pins rc0. The current registry metadata contains a real peer mismatch; a clean RC-latest install needs verification or documented in-project compatibility handling under [issue502](https://github.com/carere/zaidan/issues/502#issuecomment-5605618124). `^2.0.0-rc.0` ranges from primitives and Sonner also do not by themselves prove compatibility with later API changes.
4. **Keep Sonner branch as animation reference:** approved direction already names exact commit957eda6 and animation parity. No newer migration branch change found, so this aspect is unchanged.
5. **No assigned package lands in “no release and no public migration work found”:** all packages in this slice have a published v2 track, an open migration PR, or a public migration branch. Canonical Corvu's stale branch should not be presented as ready.

This investigation did not install, execute or browser-test packages. A declared v2 peer range and migration branch establish upstream intent and distribution, not Zaidan's SSR/hydration, interaction, visual or registry installation release gates.

## Important current-RC gap

The npm tarball for Router `2.0.0-rc.8` still reads `Solid.sharedConfig` in `src/ClientOnly.tsx` and `src/registryTransfer.ts`. [#8569](https://github.com/TanStack/router/pull/8569), merged 2026-10-01, removes those internal reads and switches to `isHydrating`, `isHydratable`, `getHydrationWriter`, and `takeHydrationValue` in Solid rc.13. The maintained branch raises Solid/web peer floors to `>=2.0.0-rc.13 <3.0.0` and uses `@solidjs/vite-plugin ^3.0.0-next.46`. [The open release PR](https://github.com/TanStack/router/pull/8468) includes that fix; npm still exposes RC8/RC6. Therefore **published Solid 2 support exists, but the latest Solid RC and latest published TanStack RC are not yet a proven matched set**. Do not automatically combine floating `@rc` dependencies without SSR/hydration verification. The upstream PR also documents a compiler/runtime event-key change between earlier RCs, reinforcing the need to align compiler and runtime versions.

## Transitive details

Published Router RC8 declares `@solidjs/meta ^0.29.4`, `@solid-primitives/refs ^1.0.8`, and `@solid-devtools/logger ^0.9.4`. Their registry metadata respectively declares Solid `>=1.8.4`, `^1.6.12`, and `^1.9.0`. A scan of RC8's published ESM imports found **no actual imports of these three packages** in its built JS. They still matter for installation/peer resolution, but should not be called confirmed runtime blockers solely from metadata. `router-devtools-core@1.168.1` has no Solid dependency or peer in published metadata, because its Solid runtime is bundled; #6838 explicitly explains that separation. Start's shared `router-core`, `start-client-core`, `start-plugin-core`, and `start-server-core` retain their own independent v1 version numbers; their v1 numbering is not proof of Solid 1 dependency.

## Dependencies that do not require a Solid migration

The remaining direct manifest dependencies are framework-neutral tooling, data libraries, styles and fonts: `@cloudflare/vite-plugin`, `@date-fns/tz`, all `@fontsource` / `@fontsource-variable` packages, `@internationalized/date`, `@mastra/core`, `class-variance-authority`, `clsx`, `date-fns`, `effect`, `shadcn`, `tailwind-merge`, `ts-pattern`, `zod`; and the dev tooling for Biome, Expressive Code, MDX/unified/remark/rehype, Moon, Playwright, Tailwind, TypeScript, Bun types, Velite, Vitest, happy-dom, Knip, Lefthook, package sorting, stripping indentation and Wrangler. They are not Solid adapters and should not be counted as “not migrated.” Framework-neutral does not establish full website integration compatibility. In particular, Vite transforms, test aliases and Cloudflare SSR need checking with the migrated application.

The existing Cloudflare plugin1.50.0 has Vite8-compatible peers and no Solid peer; upgrading it is not necessary solely for Solid2. Newer Cloudflare1.62.5 also peers Wrangler `^4.147.0`, so an unrelated upgrade is not a free single-package substitution. [Existing manifest](https://registry.npmjs.org/@cloudflare/vite-plugin/1.50.0), [new manifest](https://registry.npmjs.org/@cloudflare/vite-plugin/1.62.5). MDX3.1.1 emits JSX for downstream compilation; the incompatible dependency is the provider, not the generic compiler.

## Recommended branch follow-up

1. Use runtime/web/compiler/Babel **rc.13** and renamed Vite plugin **next.47** as the refreshed exact candidate baseline. Keep TanStack-owned routing/SSR; do not enable the Solid plugin's separate framework mode just to update the compiler. Wait for the pending TanStack compatible RC release or reuse its pinned upstream changes under the existing bridge policy.
2. Replace the proposed Lucide compatibility bridge with released **`@lucide/solid@1.52.0`** during implementation. Update all imports, registry dependency metadata and preprocessing together; plugin1.8.0 recognizes the new namespace. The existing plugin1.5.3 has not been validated with that namespace.
3. Assess upstream **MDX PR4** before creating provider compatibility code. Preserve intrinsic wrappers, nested providers and overrides; validate client rendering and SSR/hydration. Record the immutable upstream commit for any local bridge.
4. Retain the approved Kobalte replacements and v9 Embla direction. Cmdk's published support and Corvu's community fork are alternatives worth knowing about, not authorization to reverse settled decisions. Reconcile Kobalte core/utils exact RC peer mismatch and unreleased branch fixes against the selected runtime.
5. Table and Virtual still need temporary adapter work or compatible upstream releases. Embla and Sonner have public migration PRs. Dnd-kit has no discovered Solid2 work, but the approved replacement already has a published Solid2 package.
6. Migration must update installable registry dependencies as well as the website manifest. Current `src/registry/kobalte/registry.json` includes unversioned Solid1 adapter names and specifically pins charts to `solid-recharts@1.0.1`; regenerating artifacts without changing source dependency metadata would still install the wrong libraries. Apply the existing showcase policy until clean consumer installation is possible.
7. Keep PR501 draft. The [bridge/removal policy](https://github.com/carere/zaidan/issues/502#issuecomment-5605618124) still requires stable Solid2 and compatible upstream releases replacing every temporary bridge before merging to main. Published prerelease support is progress, not fulfillment of that release gate.
